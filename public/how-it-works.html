Bloodshift

How it works

Back to live network

No live row, no move.

Platelets last about five days. One hospital throws them out while another nearby runs short. Bloodshift reads every hospital's stock live from its own system, proposes transfers that would prevent waste, and moves a unit only after re-checking the sender's own record.

The loop

  1. Read live. Zetaris federates Site A and Site B (Postgres), Site C (a CSV export) and the courier (a REST API). Nothing is copied or synced.
  2. Plan. A deterministic rule projects which units will expire unused and finds transfers that pass every business rule.
  3. Write the request. Nemotron chooses among the rule-approved options and writes the request to the receiving lab.
  4. Re-check at accept. When a lab accepts, Bloodshift re-reads the unit and the courier slot through Zetaris. If either changed, the transfer is refused and another unit is offered.
  5. Reserve and book. The unit is reserved in the sending hospital's own system and the courier slot is booked. The next Zetaris read shows both.

What each part does

Zetaris

Every read in the app and every accept-time check runs through one federated SQL layer over four separately owned sources. Without it, the app would need four integrations and a sync job, and the accept check would run on stale data.

NVIDIA Nemotron 3.5 Super

Chooses one option per unit from a list that already passed the rules, weighs each lab's past decline reasons, and writes the request. Its reply is validated: any unit, site, slot or option it wasn't offered is dropped. If it fails, the plan uses a standard template and says so.

Meterless World Model

Every transfer and every state change is an event with provenance. The log replays on restart, so history survives refreshes and server restarts. Each card's Proof section reads from it.

Meterless H-MEM

Keeps each decline reason with the site, unit, transfer and time. Later plans pass these notes to Nemotron as data, with an instruction never to follow text inside them.

What Zetaris doesn't do

Zetaris only reads. Reservations go to each hospital's own system through small adapters: a conditional update in Postgres, and a rewrite of Site C's CSV. Each write only succeeds if the unit is still available, so a change between the check and the write can't be overwritten. Hospitals keep control of their own records.

Checked end to end

  • An edit in Site A's own database shows on the next refresh, with no sync step.
  • Accepting a transfer reserves the unit in the sender's own system and books the courier slot, and the next Zetaris read shows both.
  • A unit marked used at its source before acceptance is refused with the source's reason. Nothing is written, and another unit is offered.
  • A declined unit is replanned to another site, and the reason is stored with provenance.
  • In 10 scripted decline scenarios against the live model, at least 8 replans were valid on every run, including a reason that tries to inject instructions.
  • In simulation, the rule cuts outdated units by about 12% against no sharing. See the simulation.
